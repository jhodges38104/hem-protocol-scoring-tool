# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

A static, dependency-free single-page app that scores hospital clinical-trial protocols against the "Non-Malignant Hematology Protocol Complexity & Workload Rubric (Draft v0.2)." Part A produces a 37-item, 8-domain weighted complexity score (0–116); Part B turns that score plus live participant counts into a Monthly Workload Index (WU) — scaled by a data volume factor on the participant term — with an optional WU→FTE conversion. Everything runs client-side — no backend, no network calls. Live at https://jhodges38104.github.io/hem-protocol-scoring-tool/.

**v0.2 (Domain 8 + data volume factor)** was added in response to a review question — "how does this capture something very data-entry heavy, on the scale of ATHN or MOTIVATE?" — that found v0.1's Domain 5 cap left data-entry-heavy, visit-light registries unable to score above ~Tier 2. It's additive: v0.1's seven domains, their weights, and TIERS are byte-for-byte unchanged, so a protocol scoring zero on every Domain 8 item scores and tiers identically to v0.1. Full rationale: `docs/rubric.md`'s "v0.2 change note" and Domain 8/Part B sections.

The rubric is an explicitly unvalidated draft (see the disclaimer in `README.md` and the validation plan in `docs/rubric.md`); the app computes its arithmetic faithfully but doesn't claim the weights are calibrated — e.g. the FTE figure is deliberately labeled "this protocol only," not "Required FTE."

## Commands

There is no build step, package manager, or linter — no `package.json`, `Makefile`, or lint/format config exists anywhere in the repo. Per `README.md`, that's a deliberate design goal, not an oversight: the app has no framework, bundler, or external network calls "so this runs unmodified on a hospital network and stays auditable by reading three files." Don't introduce build/lint tooling unless asked to. `tests/invariants.js` is the one exception and holds the same line — a single dependency-free script, no runner, no config.

- **Preview:** open `index.html` directly in a browser (`open index.html` on macOS), or serve the directory with any static file server (e.g. `python3 -m http.server`) if you prefer a URL. If autosave or the "restored an unsaved entry" banner seems to misbehave, try the http-server route — `file://` origins don't handle `localStorage` consistently across all browsers, so it's the safer default specifically for testing persistence.
- **Test a change:** `node tests/invariants.js` from the repo root, or without a Node install, `/System/Library/Frameworks/JavaScriptCore.framework/Versions/Current/Helpers/jsc tests/invariants.js` — macOS ships `jsc`, and the script runs unmodified under both. It exits non-zero on failure and CI gates the deploy on it. It loads the real `app.js` against a stub DOM (indirect `eval`, so top-level `const`s stay reachable) and asserts the things this file warns will break silently: the domain maxima sum, the first seven domains still totalling 100, the tier cutoffs, v0.1 equivalence when Domain 8 is all zero, the data volume factor's range and what it may touch, CSV header/row alignment, and both older-state loaders. **Add an assertion there whenever you touch `DOMAINS`, `TIERS`, `STATUS_ROWS`, `STATIC_WU`, or the Part B formula.** It does not cover rendering, print layout, or event wiring — for those, still verify by hand in a browser, including an Export JSON → Import JSON round-trip.
- **Deploy:** not a local command — see Deployment below.

## Deployment

`.github/workflows/pages.yml` is the current and only deployment mechanism. It runs two jobs: a `test` job (`node tests/invariants.js`, no install step since there are no dependencies), then `deploy` with `needs: test` — `actions/checkout` → `actions/configure-pages` → `actions/upload-pages-artifact` (`path: '.'`) → `actions/deploy-pages`. Triggered on every push to `main` or manually via `workflow_dispatch`. **A failing invariant blocks the deploy**, which leaves the previous version live rather than publishing a broken scale. Live at https://jhodges38104.github.io/hem-protocol-scoring-tool/.

Two things worth knowing that aren't obvious from the workflow file alone:
- **`path: '.'` publishes the whole repo root**, not just `index.html`/`app.js`/`styles.css`. `docs/` (including the source PDF) and `README.md` are live and publicly fetchable too — confirmed by loading `docs/rubric.md` directly at the deployed URL. Anything added at the repo root, including this file, becomes publicly served on the next push to `main`.
- **This repo has to stay public.** GitHub Pages on a private repo requires GitHub Enterprise Cloud; per `README.md`, switching this repo to private would take the live site down unless that tier is available.

## Architecture

The whole app is three files with no imports or modules between them: `index.html` (structure) loads `styles.css` in `<head>` and `app.js` (~600 lines, all logic) via a plain `<script>` at the end of `<body>`. `app.js` wraps its own startup in a `DOMContentLoaded` listener. There is no other JS file and no framework.

### Rubric content is data, not scattered logic

All 37 scoring items live in one `DOMAINS` array literal near the top of `app.js` — 8 domains, each with `id`/`title`/optional `cap`/an `items` array (`id`/`label`/`max`/`note`/optional `dataVolume`). A loop immediately after the literal derives each domain's `itemizedMax` and effective `max` (`cap` if present, else `itemizedMax`) once, rather than duplicating it by hand. Sibling tables in the same style hold the rest of the rubric's numbers: `TIERS` (score band → tier), `STATUS_ROWS` (participant status → per-tier WU), `STATIC_WU`, `PHASE_MULTIPLIERS` (with `DEFAULT_PHASE` naming the one the `<select>` preselects, `resetFormToDefaults()` writes, and `computeAll()` falls back to — one constant so those three can't disagree). **To change a weight, add an item, or move a tier boundary, edit these tables — the render and compute functions just iterate over them generically and shouldn't need to change.**

### The DOM is the source of truth

This is a direct comment in `app.js`, not a paraphrase. There's no persistent JS object mirroring form state. `collectState()` reads every input's live `.value` into a fresh plain object on every call; `applyState(s)` is its inverse, writing a plain object back into the form (used for both localStorage restore and JSON import). `computeAll()` always starts by calling `collectState()` fresh — nothing is cached between calls. **A new field has to be wired into both `collectState()` and `applyState()`, or it silently won't persist, export, or restore.**

### One render orchestrator, one report node for screen and print

`update()` fires on every `input`/`change` event and runs, in order: `computeAll()` → `updateDomainSubtotals()` → `renderPartBBreakdown()` → `renderFteReadout()` → `renderReport()` → `saveToLocalStorage()`. `#report` in `index.html` is filled only by `renderReport()`, and it **is** both the live results panel and the printed report — there's no separate print view to keep in sync. Screen-vs-print differences are pure CSS: elements that should vanish on paper (the input form, restore banner, footer) carry a `.no-print` class, hidden by `@media print` in `styles.css`, which also flattens the two-column layout and forces the light-mode CSS variables regardless of the viewer's OS dark-mode setting, so a printed/PDF report is always legible. (Confirmed working via the browser's print dialog this session.)

### Persistence and export, no backend

`update()` autosaves to `localStorage` (key `hemProtocolScoringTool.v1`) at the end of every call, wrapped in try/catch for private-mode/quota failures. Export JSON / Import JSON round-trip the full `collectState()` output, which carries a `schema` field (currently `2`, separate from `TOOL_VERSION`). **Both loaders check it** — `onImportJsonFile()` and the autosave restore in `init()` (via `showRestoreBanner()`) — and warn if it differs, see the magic-numbers section below. Both also gate on `isPlausibleState()` first. The CSV export — labeled "Reliability CSV row" in the UI, not a generic export — writes one wide two-row file (header + one data row of every item score and computed field), shaped specifically so exports from multiple scorers can be pooled for the inter-rater reliability analysis `docs/rubric.md`'s validation plan calls for. Destructive actions (Import JSON's overwrite, New/Clear form) share a reusable confirm pattern, `wireArmedButton()`: the first click arms the button (relabels it, starts a 4-second auto-disarm timer) only if there's unsaved data to lose; a second click within the window confirms.

### Runtime-generated DOM and an undeclared CSS contract

`index.html` provides static page chrome plus four empty mount points `app.js` fills at runtime: `#domainsRoot` (via `generateDomains()`, the first line of `init()`), `#phaseSelect` (via `generatePhaseOptions()`, which must run **before** any `applyState()` — setting a `<select>`'s value is a no-op if the matching option doesn't exist yet, so a restored or imported phase would silently drop to the default), `#partBBreakdown`, `#report`. Element IDs like `item_${id}` and `subtotal_${id}` are built from the `DOMAINS`/`STATUS_ROWS` tables and don't exist anywhere in the static HTML — don't go looking for them there, and don't rename an item's `id` without checking the template strings that build IDs from it. `styles.css` and `app.js` also share an **undeclared class-name contract**: classes like `.domain`, `.item-row`, `.tier-badge`, `.wu-table` are emitted only by `app.js` template strings and styled only in `styles.css`. There's no CSS Modules/scoping, so renaming a class in one file silently breaks styling in the other with nothing to catch it.

`index.html` used to share a second such contract, and it was worse because it changed results rather than looks: the phase `<select>` restated all five `PHASE_MULTIPLIERS` ids and values as static markup, and `computeAll()` resolves a phase with `PHASE_MULTIPLIERS.find((p) => p.id === s.phase)` and **falls back** rather than erroring — so renaming an id in the table alone silently costed every protocol at the `DEFAULT_PHASE` rate. That contract is gone: `generatePhaseOptions()` builds the options from the table, `#phaseSelect` is a mount point like `#domainsRoot`, and adding or renaming a phase now means editing `PHASE_MULTIPLIERS` only. `tests/invariants.js` section 7 asserts the duplication stays gone and that every generated id round-trips through `computeAll()`.

Two headings still ship a number in the markup, deliberately: the Part A ceiling (`#partAMaxLabel`) and the Part B data-volume range (`#dataVolumeRangeLabel`) are correct as written so the page reads sensibly if the script fails, and `init()` overwrites both from `PART_A_MAX` / `DATA_VOLUME_FACTOR_RANGE`. The tests assert the overwrite happens, so a stale fallback can't go unnoticed.

**Display multipliers with `fmt1()`, never raw.** `String(1.0)` is `'1'`, so a bare `×${phase.value}` renders steady state as "×1" where every written version of the rubric says ×1.0. All four sites (the generated options, both Part B breakdown tables, and the report's help line) go through `fmt1`.

## Non-obvious rules and magic numbers

- **Domain 5's cap is deliberate.** Its items sum to 18, but `cap: 16` limits its contribution to the total (`d.cap != null ? Math.min(raw, d.cap) : raw` in `computeAll()`), because the domain maxima are meant to sum to exactly 100 in v0.1 (18+12+18+12+**16**+12+12) / 116 in v0.2 (+ Domain 8's 16). Changing any domain's items without checking this sum will break it silently. Domain 8 itself has **no cap** — its five items sum straight to its 16-pt contribution, unlike Domain 5.
- **`PART_A_MAX` is computed, not hardcoded** — `DOMAINS.reduce((sum, d) => sum + d.max, 0)`, defined right after the domain-max-deriving loop, and used everywhere `app.js` needs the Part A ceiling (report summary tile, Part A total line). This replaced a v0.1 pattern where "100" was a hardcoded literal in three places. The third — `index.html`'s Part A heading — is now filled from the constant too: the markup still ships `(116 points)` so the heading reads correctly with JS disabled, and `init()` overwrites it from `PART_A_MAX` via `#partAMaxLabel`. `tests/invariants.js` asserts the element exists and that `init()` fills it, so the fallback literal can't quietly become the wrong number.
- **The data volume factor (v0.2) scales only the participant-WU term, not Static WU.** `DATA_VOLUME_ITEMS` (in `app.js`, derived via `DOMAINS.flatMap(...).filter(it => it.dataVolume)`) is currently exactly two Domain 8 items — `chart_abstraction` and `diary_pro_frequency` — flagged with `dataVolume: true` in their `DOMAINS` entries. `computeAll()` sums those two raw scores against `DATA_VOLUME_MAX` (7) to get a factor in `[1.0, 1.3]` (`DATA_VOLUME_FACTOR_RANGE = 0.3`) and multiplies each `STATUS_ROWS` subtotal by it. Domain 8's other three items (DCC cadence, sub-study count, lifetime horizon) deliberately do **not** feed this factor — they're protocol-level facts that already raised the Part A total and therefore the tier (which sets `STATIC_WU` and every `STATUS_ROWS` rate); including them here too would double-count them. If you add a new Domain 8 item that's genuinely per-encounter, flag it `dataVolume: true` and it's picked up automatically — nothing else needs editing. If it's structural, leave the flag off.
- **The phase multiplier applies to the protocol total**, `(staticWU + participantSubtotal) × phase.value`, not just the participant term. This is a deliberate interpretive call: the source rubric's formula notation reads ambiguously under normal operator precedence, but its multiplier table is explicitly captioned to apply to the total. Documented in a comment directly above `PHASE_MULTIPLIERS` in `app.js` and in `README.md`'s "Interpretive decisions" section. Also deliberate: **only one multiplier is ever applied** — `phaseSelect` is a single `<select>`, so if two conditions land in the same month (e.g. a substantive amendment during startup), the rubric doesn't define stacking and this tool doesn't invent one; `index.html`'s help text says to pick the single most applicable condition or apply your own documented convention. Don't add multi-condition stacking without resolving that gap first.
- **Participant counts clamp to `[0, 999999]`** as a practical unbounded ceiling, applied in both `computeAll()` and the CSV export.
- **Three separate version concepts exist — don't conflate them:** `TOOL_VERSION` (`'2.0.0'`, this app's own version — bumped for the v0.2 rubric change), `RUBRIC_VERSION` (`'Draft v0.2'`, the source instrument's version, shown wherever the UI needs to remind the reader the instrument is unvalidated), and the JSON export's `schema` field, now `SCHEMA_VERSION = 2` (bumped from 1 specifically because v0.2's five new Domain 8 item ids mean a schema-1 export is missing data a schema-2 reader expects — this **did** change the export's shape, unlike the rest of v0.2, which only added item ids already covered by the generic `for (const d of DOMAINS)` loops in `collectState()`/`applyState()`/`exportCsv()`). Both paths that can load an older state compare it against `SCHEMA_VERSION` and warn (neither blocks): `onImportJsonFile()` for a JSON import, and `showRestoreBanner()` for `init()`'s autosave restore, sharing one wording via `schemaGapMessage()`. The reason is `applyState()`, which silently leaves any item id absent from the loaded state at its current form value (0 by default) — without the warning, a pre-v0.2 state produces a plausible-looking but incomplete score with no indication anything is missing. **The restore path matters more than the import path**, since reopening the tool restores the last entry automatically and every returning scorer hits it, whereas import is occasional. `LS_KEY` deliberately stays `'…​.v1'` rather than being bumped: a new key would silently discard a staffer's in-progress entry instead of showing it to them with a warning. `isPlausibleState()` guards both loaders on the same items+meta criteria — `init()` has no try/catch, so a malformed payload reaching `Object.values(s.meta)` inside `hasAnyData()` would abort startup before `wireEvents()`/`update()` and leave a rendered but inert page.

## Documentation structure

`docs/rubric.md` is the canonical source for every rubric number — it says so explicitly ("Numbers here are the single source of truth for this project"). `docs/quick-guide.md` (a ~10-minute operational walkthrough) and `docs/user-guide.md` (longer reference: two-scorer reconciliation workflow, an "interpreting your result" section, FAQ, glossary) both link into specific `rubric.md` anchors instead of restating its tables. `docs/TrialComplexityRubric.pdf` is the original source document `rubric.md` transcribes and reorganizes.

This is a separate hierarchy from `app.js`'s `DOMAINS`/`TIERS`/etc. tables, which are the source of truth for the *running code*. Nothing links the two — they're independent, hand-maintained descriptions of the same numbers. A weight changed in one won't propagate to the other; changing a rubric number means updating both `app.js` and `docs/rubric.md` yourself.
